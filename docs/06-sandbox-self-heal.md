# 1. 自愈闭环总览

为保障高 AC 率并减少对 LeetCode 的无效请求，测试流程严格遵循以下闭环：

```
[ 获取题目/样例 ] ──> [ AI 编写代码 ]
                             │
                             v
                    [ 本地沙盒运行测试 ] ──(失败)──> [ 提取本地报错日志 ]
                             │                               │
                             │ (全通过)                       └─> [ AI Self-Debug 重试 (≤4 轮) ]
                             v                                           ▲
                    [ 提交 LeetCode ]                                     │
                             │                                           │
                 ┌───────────┴─────────────┐                             │
                 v                         v                             │
             [ AC ]                  [ WA / TLE / RE ]                   │
                 │                         │        WA: 提取失败用例     │
                 v                         ├──────────────────> [ 动态追加本地用例库 ]
          [ 触发题解生成 ]                   │                            │
                                   ├─ TLE: 无完整输入 ─> [ 复杂度反思 ] ──┤
                                   └─ RE: 本地复现优先 ─> [ 健壮性反思 ] ─┤
                                                                │        │
                                                                v        v
                                                   [ 本地重跑 → 第 2 次真实提交 ] ─(仍失败)→ [ skipped ]
```

# 2. 沙盒安全模型（强制要求）

AI 生成的代码是**任意代码**。超时只能杀死死循环，杀不死意外或恶意行为（读写文件、发起网络请求、内存炸弹、进程逃逸）。因此每次沙盒执行必须满足：

* **一次性执行环境**：每次运行使用全新容器或非特权子进程，运行结束即销毁，不与主进程共享任何可写状态。
* **资源与权限硬限制**：
  * 网络：**完全禁止**出/入站连接；
  * 文件系统：根只读，仅注入题目输入文件至一次性临时目录（用后即焚）；
  * 内存上限（如 512 MB）与 CPU 时间上限（如 3 秒）双门限，外加进程数上限；
  * 以非特权用户身份运行。
* **纵深防御**：执行前做静态扫描（模块依赖白名单、危险 API 检测）作为辅助层，但它**不是**安全边界；禁止以 `node --eval` 直跑或裸 `vm` 模块充当隔离（后者不是安全机制）。
* **上下文隔离**：沙盒环境不得持有 Cookie、GitHub Token 等任何系统凭据。

# 3. 动态数据还原与 Driver 生成

* **不人工枚举类型**：基于 LeetCode 题目元数据（code definition / `metaData` 中的函数签名与类型模板）**自动生成**序列化/反序列化 driver。
* **类型映射表**需覆盖：一/多维数组、字符串、单链表 `ListNode`、二叉树 `TreeNode`、随机指针 `Node`、循环链表（`pos` 表示法）、嵌套结构等。
* **Driver 黄金用例库**：为每条类型映射规则维护已知正确/错误的序列化样本，driver 生成器纳入单元测试，保证回归可控。
* **不可识别类型**：凡元数据中出现映射表之外的结构，该题直接标记 `unsupported` 跳过，绝不猜测结构后提交。
* 本地比对采用"运行后反序列化再结构化对比"，浮点数比较带容差。

# 4. 失败分流（WA / TLE / RE 不走同一条路）

从 LeetCode 报错中提取信息的能力是**有边界的**，必须按 verdict 分流：

| Verdict | 可提取的信息 | 处理路径 |
|---------|--------------|----------|
| WA | 失败用例的输入/期望输出（非比赛题可用；大输入会被截断） | 追加至本地用例库（标记 `truncated`），本地重跑修复 |
| TLE | **无完整输入**（且往往是超大输入） | **不追加用例**；将"超时"信号传入 AI 做**复杂度反思**，要求更优算法 |
| RE | 报错信息；输入可能缺失 | 优先在本地复现（stderr 可用）；无法复现时走**健壮性反思**路径 |

分流后仍失败达重试上限的，按 `skipped` 处理（参数见 [05-scheduler.md](05-scheduler.md)，终态定义见 [03-state-machine.md](03-state-machine.md)）。

# 5. 本地门限的定位

* 沙盒硬超时（3 秒）是**防爆门限**，不是判题标准：本地与 LeetCode 判题机硬件不同，本地耗时只能作启发式参考，不得因本地接近门限而放弃提交。
* 本地通过 ≠ AC：本地用例库（初始样例 + 回填失败用例）只是提交前的最低门槛，接受残余失败率。

# 6. 与其他模块的接口

* 每次 LLM 调用（生成 / self-debug / 反思）的 token 计量与预算约束见 [08-ai-budget.md](08-ai-budget.md)。
* 每次真实提交的代码快照、verdict、报错摘要落库于 `attempts` 表（见 [10-data-protocols.md](10-data-protocols.md)）——无此记录则自愈过程不可复盘。

# 1. 系统目标与定位

本系统是一个托管在服务器上的 24 小时无人值守刷题与监控平台。
系统采用 **JavaScript/TypeScript 全栈** 架构，通过 **前端可视化控制台 + 后端异步任务引擎 + 本地沙盒 + AI 大模型**，实现以下核心诉求：

1. **控制自治**：支持随机刷、顺序刷、按标签/难度刷，并可随时手动暂停、恢复、单次触发。
2. **账号与风控感知**：实时监控 LeetCode Cookie 有效性，自动引入人类行为模拟与动态冷却，避开风控。
3. **本地防错闭环**：AI 代码先过本地沙盒校验；提交 LeetCode 报错后自动扩充本地用例库再重试。
4. **状态透明化**：通过 WebSocket 向前端控制台实时推送当前运行节点、历史数据与运行日志。

# 2. 范围与非目标

明确以下边界，避免需求蔓延与风险放大：

* **单实例、单账号、单并发**：同一时刻至多运行一道题目的流程。这是风控目标决定的**设计约束**，不是缺陷。
* **不做** 多账号轮换、分布式刷题、比赛/周赛自动参赛——这些会显著放大风控暴露。
* **不做** 未经本地沙盒验证的直接提交。
* 支持 LeetCode 中文站/英文站其一（可配置站点域名），不追求同时双站。

# 3. 风险声明与合规对策（必读）

自动化提交**极可能违反 LeetCode 服务条款**（反自动化/反爬取条款），存在限流、CAPTCHA 频发、封号乃至封 IP 的现实风险，后果由运营者自行承担。系统设计必须内置以下止损机制：

* **小号原则**：仅允许配置可牺牲的非主力账号；系统不提供任何对抗性伪装能力。
* **限频硬顶**：对 LeetCode 的所有出站请求**全局串行**，最小间隔 ≥ 5 秒；每日真实提交配额默认 ≤ 10 题（可配置下调）。实现要点见 [04-auth-risk.md](04-auth-risk.md)。
* **分级熔断**：见 [04-auth-risk.md](04-auth-risk.md)。触发 CAPTCHA 即熔断；单日 CAPTCHA ≥ 2 次自动停机 24 小时。
* **一键 Halt**：任何时刻可发出终止指令，软化停止一切对外请求（状态语义见 [03-state-machine.md](03-state-machine.md)）。
* **Plan B 抽象**：`Submitter` 定义为接口层（本地判题 / 私有 OJ 适配器可实现同一接口），更换提交目标时，其余架构（见 [02-architecture.md](02-architecture.md)）不变。
